# 会诊材料：Lumia 950 ARM32 UWP 上 WebKit 2.52 的两个未决闪退

> 2026-10-07 晚整理。**给接手专家的一页式情况说明**，目标是让人不看代码也能复现、看证据、
> 知道什么已排除。项目背景见 `AGENTS.md` / `docs/HANDOFF.md`（§10 是同一天的根因记录）。
>
> **一句话**：0.2.4.4→0.2.5.8 的主回归（空指针）已定位并修复、真机验证通过；
> 但暴露出**两个独立的未决崩溃**：(A) baseline JIT 开着就执行违例，(B) `ScheduledTask`
> 生命周期导致 SIGABRT。(B) 我修了一轮但没修对，仍是当前阻塞。

## 3. 现象清单（按崩溃签名分组，全部真机记录）

### 已修：空指针 `VM::jitStubs == nullptr`（0.2.4.4→0.2.5.8 的主回归）

崩溃链（`crash\Harness.exe.6296.dmp` 已符号化）：

```
WebEngine::loop → WebCoreSessionLoad → RunLoop → CurlDidReceiveData
→ ScriptElement::executeClassicScript → ScriptController::evaluateInWorld
→ JSWindowProxy::create → JSDOMWindow::finishCreation
→ JSGlobalObject::init → FunctionPrototype::addFunctionProperties
→ JSObject::putDirectNativeFunctionWithoutTransition → JSFunction::create
→ VM::getHostFunction → JITThunks::hostFunctionStub    ← this == nullptr
→ HashTable<Weak<NativeExecutable>>::find → ldr r7,[r0]，r0 = 0x3C0
```

**根因**：`VM::VM`（`runtime/VM.cpp`）只在 `if (Options::useJIT())` 时创建 `jitStubs`；
但 JITThunks 的消费者**不看 useJIT**：

- `VM::getCTIStub()`（`runtime/VM.cpp:846-849`）**完全没有 `if (Options::useJIT())` 守卫**
- `VM::getHostFunction()`（892-905）的守卫是针对**整个 LLInt/JIT 分流**的
- `InlineCacheCompiler::emitExplicitExceptionHandler()`（`bytecode/InlineCacheCompiler.cpp:1327`）直接调 `getCTIStub`

harness 的 `ApplyJitSetting()` 往引擎线程 post `WebCoreSetJitEnabled()`，与首个
Page/VM 创建**竞态**：VM 建在 `useJIT==0` 时 → 不建 `jitStubs` → 后续任何走 thunk 的路径
空指针。0.2.4.4 是 `ENABLE(JIT)` 编译期就关了，整条机器不存在 → 无回归。

**修法**（`Source/JavaScriptCore/runtime/VM.cpp`，WK_WINUWP 守卫 + 注释）：
```cpp
if (Options::useJIT() || ExecutableAllocator::singleton().isValid()) {
    jitStubs = makeUnique<JITThunks>();
    jitStubs->initialize(*this);
    ...
}
```
语义：**可执行池可用就必须有 JITThunks**——它不是 JIT 执行期专属，LLInt 的 IC/异常 thunk、
host function 桩都在里面。池无效仍跳过（保住 0.2.4.3 教训：`JITThunks::initialize()`
会在空 code 指针上 patch）。

**真机验证通过**（0.2.5.9）：`useJIT=0 canUseJIT=1` + `after-load rc=0`，JS 真跑。
单次交互会话连续加载 pigai.shop / deepseek.com / chat.deepseek.com 全 `rc=0`。

### 未决 A：`useJIT==true` → 执行违例，跳靶在 JIT 池外低位地址

4 次运行，形态完全一致（`pc` = 跳靶地址，`lr` = 返回地址）：

| 版本 | 时间 | pc | lr |
|---|---|---|---|
| 0.2.5.9 | 19:23:24.877 | `0x00000100` | `0x1c11f287`（池内） |
| 0.2.5.9 | 19:23:46.339 | `0x00000100` | `0x1bb1f449`（池内） |
| 0.2.5.9 | 19:24:42.064 | `0x00040000` | `0x1c411b15`（池内） |
| 0.2.5.10 | 21:30:09.611 | `0x00040000` | `0x1c711b15`（池内） |

```
SEH code=0xc0000005 address=0x00040000 access=8 fault=0x00040000
context: pc=0x00040000 lr=0x1c711b15 r0=0x27ba0e08 r1=0xfffffffb
reason: jit pool: [0x1c710000, 0x1e710000) isJITPC(fault)=0
```

读法：CPU 试图在 `0x40000` 取指 → **控制流跳到了一个非代码地址**；而 `lr` 在 JIT 池内 →
**发起这次调用的是 JIT 生成的代码**。`access=8` 是取指违例，不是数据访问。
`r1=0xfffffffb` 三次都一样。

**先更正我上一轮的说法**：这是 4/4 的经验规律，**机理并未证明**。我说"必崩"是统计描述，
不是根因分析，措辞过头了。

#### 候选机理（按我认为的可能性排序，均未验证）

1. **thunk 表没填满 / 填错。** `JITThunks::initialize()`（`jit/JITThunks.cpp:52-59`）用
   `JSC_FOR_EACH_COMMON_THUNK` 宏填 `m_commonThunks[]`；`VM::getCTIStub(thunkID)`
   （`JITThunks.cpp:198-203`）直接下标取，只有一个 `ASSERT(result)`。
   若某 thunk ID 未初始化或越界 → 拿到一个"看着像指针其实是小整数"的 `ExecutableMemoryHandle`。
   `0x100`/`0x40000` 这种规整低位值与此假设相容。
   **判别**：在 `VM::VM` 里加断言遍历 `m_commonThunks` 检查全部非空且代码落在池内。
2. **LLInt↔JIT 衔接在本 port 上是错的。** ARM32 Thumb-2 下 LLInt 的 `vmEntryToJavaScript`/
   `ctiVMThrowTrampoline` 与 baseline JIT 的入口约定若有偏差，跳靶就会变成垃圾。
   **判别**：只跑 LLInt 一段（`useJIT=0` 现在稳定）vs 立即 tier-up（`JSC_useJIT=1` +
   降低 tier-up 阈值）对比。
3. **WK_WINUWP 补丁的语义副作用。** JIT 编译期落了 7 个补丁（`docs/JIT-254-PORTING.md`），
   为绕编译错误可能改坏了某个不变量。
4. **W^X 与代码写入竞态。** 池路径是 `VirtualAllocFromApp` RW → `VirtualProtectFromApp` RX
   （`wtf/win/OSAllocatorWin.cpp`）。若 JIT 代码还在 RW 页上执行应是 DEP 违例、
   故障地址应在池内——实测 `isJITPC(fault)=0`，**所以这条基本可以排除**。
5. **ARM32 baseline JIT 本身在此 clang 版本上有 codegen bug。**

#### 历史事实（别重新查）

- `AGENTS.md` 明确记载：三条历史线的 `JavaScriptCore.lib` 里
  `startOfFixedExecutableMemoryPoolImpl` 计数**都是 0**——**JIT 从未在任何出货构建里启用过**；
  `harness/JitProbe.cpp` 只验证了可执行内存原语（RW→RX / RW→RWX 三场景），
  **没有验证过 JIT 本体**。
- `docs/JIT-HANDOFF.md` §4 记着"已落地、启用后仍保留的 7 个编译期修复"与撞墙清单。

#### 我为此做的处置（0.2.5.11 起）

驱动侧默认关 + 拒绝启用（`port/WebCoreDriver.cpp`）：

- `ensureWebCoreInitialized()` 里 `JSC::Options::useJIT() = !startsJitDisabled();`
  在 `JSC::initialize()` 之后**立刻钉死**，不给竞态留窗口
- `WebCoreSetJitEnabled(enabled)` 收到 `enable=1` 时拒绝，写一行 stage.txt：
  `jit: enable refused (ARM32 baseline JIT disabled in this port)`
- harness `ApplyJitSetting()` 会把引擎真实状态读回来同步开关 →
  **这就是用户看到的"设置里开了、重启又关掉"**（UX 问题，待用户定）

> **这个处置是产品决定，不是技术结论。** 专家会诊如果找到机理修好了 A，
> 把 `g_apoJitDisabledByDefault` 置 false 即可恢复。

### 未决 B：`ScheduledTask` 生命周期 → SIGABRT（当前阻塞）

`useJIT` 开或关都会出现（开的时候 A 通常先撞上）：

```
checked-ptr: ScheduledTask deleted with 1 CheckedPtr(s) outstanding (zeroed and leaked)
checked-ptr: released a CheckedPtr to an already-deleted object
signal 22 (SIGABRT)   ws=353M commit=209M availPhys=1387M load=46%
```

3 次记录：19:33:30 / 19:45:54（0.2.5.9）/ 21:45:30（0.2.5.11）。

含义：一个 `RunLoop::TimerBase::ScheduledTask` 被 delete 时还有 1 个 `CheckedPtr` 指着它，
之后那个 CheckedPtr 被释放 → WTF 安全机制 abort。

**相关源码**（都在 `Source/WTF/wtf/generic/RunLoopGeneric.cpp`）：

- `ScheduledTask : ThreadSafeRefCounted<ScheduledTask>, RedBlackTree<...>::ThreadSafeNode`
  （40-123 行），带 `WTF_OVERRIDE_DELETE_FOR_CHECKED_PTR(ScheduledTask)`
- `TimerBase::~TimerBase()`（317-328）：`releaseAssertIsCurrent` + `stopWithLock()`
- `TimerBase::start()`（330-337）：`stopWithLock()` → `activate()` → `scheduleWithLock()`
- `scheduleWithLock/unscheduleWithLock`（292-306）只在 `task.isScheduled()` 为真时动树
- `runImpl()`（213-239）派发队列：
  ```cpp
  auto task = firedTimers.takeFirst();
  task->fired();                                    // 无锁！回调里可能销毁 timer
  Locker locker { m_loopLock };
  if (task->isActive() && !task->isScheduled())
      scheduleWithLock(task.get());                  // 对可能已析构的 TimerBase 操作
  ```

#### 我试过的一轮（**没修对**）

在 `~TimerBase()` 末尾加了 `RunLoop::detachScheduledTaskWithLock()`：按**真实成员关系**
（走一遍 `m_schedules` 树）而不是 `isScheduled()` 旗标来摘节点，触发时写
`RunLoop::TimerBase::ScheduledTask(still linked in m_schedules; unlinked by ~TimerBase)`。

**结果：那条诊断行从未出现**（0.2.5.11 的 crash.txt / stage.txt 都没有），
说明**悬垂的 CheckedPtr 不在那个 RunLoop 的 `m_schedules` 树里**——
我对根因的假设（"节点被 free 时还挂在树里"）是错的。已部署但无效，**建议专家先别信这条**。

#### 现有线索

崩溃线程栈的噪声扫描同时出现：
```
+0x022F10F0  WTF::RunLoop::TimerBase::~TimerBase(void)
+0x022F161E  WTF::ThreadSafeRefCounted<ScheduledTask>::deref(void) const
+0x0000A204  WebCoreClickAt
+0x024370A0  MainPage::DrainUIRequests(...)
+0x0001F388  WebCorePort::takeNextUIRequest(int&, unsigned __int64&, std::string&)
+0x00420A5E  WebCore::TextureMapperLayer::paintSelf(TextureMapperPaintOptions&)
```
`~TimerBase` 与 `deref()` 相邻，可信；UI 请求链（`DrainUIRequests` → `takeNextUIRequest`
→ `WebCoreClickAt`）出现在**同一线程栈**上，值得追。

已读过的源码事实：
- `RunLoop::currentSingleton()` 是 **thread-local**（`wtf/RunLoop.cpp:70-79`，
  `ThreadSpecific<Holder>`）→ 每线程一个 RunLoop 实例、一棵 `m_schedules`
- port 里有 5 处栈上 `RunLoop::Timer`（`pumpLoop` 的 settle/watchdog、`holdPump` 的
  hold/watchdog、`WebCoreLoadUrl` 的 settle/watchdog），都是**函数局部量**
- `RunLoop::run()` 可能被嵌套调用（port 的 pump 在回调里再 `isolatedUpdateRendering()`
  跑 JS，JS 可能导航/再进 pump）→ 嵌套 `runImpl` 各有自己的 `firedTimers`
- `firedTimers` 是 `Deque<Ref<ScheduledTask>>`，是引用计数不是 CheckedPtr

#### 我还没做的取证

WTF 的 `WTFWinUWPReportDanglingCheckedPtr()`（`wtf/CheckedPtr.h:42`，实现在
`wtf/Assertions.cpp:228-231`）目前只写一行纯文本 note、**没有栈**。
打算在那里加 `RtlCaptureStackBackTrace` 写进 crash.txt，再崩一次就能看到
**是谁持有那个 CheckedPtr**。这一轮改动只在 WTF + 驱动，不需要重编引擎。
**这是我建议的下一步**，但需要你确认再动（又是一轮 -j4 重建 + 部署）。

## 4. 三个问题的关系（别混为一谈）

| # | 问题 | 状态 | 与 JIT 的关系 |
|---|---|---|---|
| 0 | 空 `VM::jitStubs` | **已修，真机验证通过** | `ENABLE(JIT)` 编进引擎 + 运行时开关 → 有此 bug；0.2.4.4 编译期关闭故无 |
| A | baseline JIT 执行违例 | 未修，**驱动默认关掉绕开** | JIT 开着才有，4/4 复现 |
| B | ScheduledTask 生命周期 | 未修，**当前阻塞** | 与 JIT 无关，开关都复现 |

注意 **A 和 B 同时存在**：0.2.5.9 同一次会话里先 A（19:23–19:24）后 B（19:33）；
0.2.5.10 只有 A（50s，比 B 更早）；0.2.5.11 关掉 A 后只剩 B（90s）。
所以"关掉 JIT 就能验证 B"这个策略是有效的，B 现在是唯一阻塞。

## 5. 给专家的具体问题

1. **A**：`pc=0x100/0x40000` + `lr` 在 JIT 池内 + `r1=0xfffffffb`，这个组合指向什么？
   thunk 表未填满（假设 1）和 LLInt↔JIT 衔接错（假设 2）怎么用最小成本区分？
2. **B**：一个 `ScheduledTask` 被 delete 时还有一个 CheckedPtr 未释放，而它**不在**
   `m_schedules` 树里——这个 CheckedPtr 还能在哪？（`CheckedPtr` 的注册表是 per-object 的，
   谁能持有一个 ScheduledTask 的 CheckedPtr？）
3. **B**：`runImpl` 里 `task->fired()` 无锁执行、回调可能析构 TimerBase，
   之后又 `scheduleWithLock(task.get())` —— 这个上游写法在嵌套 `RunLoop::run()` 下
   是否本身就不可靠？port 有 5 处栈上局部 timer，是否应该改成不依赖析构时机的写法？
4. **取证**：除了给 `WTFWinUWPReportDanglingCheckedPtr` 加栈回抓，还有什么办法在
   不出 dump 的 `abort()` 路径上拿到栈？（设备无调试器）

## 1. 崩溃三部曲（真机已验证，别重查）

详见 `docs/JIT-ARM32-R9-ROOT-CAUSE-2026-10-07.md`。摘要：

| # | 崩溃 | 根因 | 状态 |
|---|---|---|---|
| 1 | `VM::jitStubs == nullptr` 被解引用（0.2.5.8 主回归） | `VM::VM` 只在 `if (Options::useJIT())` 建 jitStubs，但 JITThunks 的消费者不看 useJIT（`VM::getCTIStub` 无守卫、`getHostFunction` 的守卫是针对分流的、`InlineCacheCompiler::emitExplicitExceptionHandler` 直接调）；harness 的 `ApplyJitSetting()` post 与 VM 创建竞态 | **已修+验证**：`ENABLE(JIT)` 下改 `Options::useJIT() \|\| ExecutableAllocator::singleton().isValid()` |
| 2 | `ScheduledTask` 生命周期 → SIGABRT | 悬垂 `CheckedPtr`。加了防护但**诊断行从未触发 → 根因仍是猜的** | **防护已加，问题开放** |
| 3 | `HTMLSelectElement::showPopup` 空 popup 解引用（apple.com 机型对比） | `protect(m_popup)` 在 null RefPtr 上构造 Ref，析构无条件 `ptr->deref()`；`PortChromeClient::createPopupMenu` 返回 nullptr 违背上游假设 | **已修+验证**：show 前补 `!m_popup` 与 `optionToListIndex()<0` 判空 |

## 2. 本日新接线（编译通过，真机未验证）

### 2.1 引擎侧复制粘贴

| 文件 | 改动 |
|---|---|
| `port/stubs-pasteboard.cpp` | `read(PasteboardPlainText&)`/`writePlainText`/`writeSelection`/`clear` 接引擎侧 buffer；**补 `Pasteboard::documentFragment()`**（唯一定义在被 DROP 的 `PasteboardWin.cpp`，所以链接器从没要过它——整条编辑链是死的）；`Editor::pasteWithPasteboard` 照抄 `editing/win/EditorWin.cpp:41` |
| `port/WebCoreDriver.cpp` | 新增 `kErrEditingRefused(-15)` + `WebCoreCopySelection/CutSelection/Paste/SelectAll`（走 `Document::execCommand()` 公开入口，因 `Editor::performCutOrCopy` 是 private）+ `WebCoreClipboardGetText/SetText`（U8 buffer 视图） |
| `port/WebCoreDriver.h` / `harness/WebCoreDriver.h` | **两份同步**（A↔B 铁律） |

踩过的坑：C ABI 全在 `extern "C"` 块里，**C++ namespace 声明在那种上下文里链接不到**（裸符号 `text`/`setText`）→ 改成 `extern "C"` 的 `apoClipboardRead/apoClipboardWrite`。

### 2.2 长按上下文菜单

`harness/MainPage.xaml` 的 LinkMenuCard 扩成通用卡：**复制链接/复制/全选/分享**四行
（Segoe MDL2 图标、L8 双语、行可见性在 `Measure` **之前**设好否则量的还是旧高度）。
`OnPageHolding` 分流：非链接且非 drag widget → `WebCoreWantsDragAt` 探测，
非 widget 走 `ShowContextMenu(false)`（**不向页面派发任何事件**，所以"长按不会误导航"
这条原有安全性不变）——原来这条是 `WebCoreLongPressAt` 的 `DRAG_WIDGET_ONLY` 早退、
什么都不做。
剪贴板搬运壳负责：`ClipboardPushToSystem` / `ClipboardPullFromSystem`（ppltasks
`create_task(GetTextAsync())->then(...)`），全程异步 post，引擎不阻塞。

### 2.3 `<select>` 下拉弹窗

`PortChromeClient::createPopupMenu` 从 `return nullptr` 改为 `WebCorePort::queueSelectPopup()`。
**关键契约**：WebCore 要求返回一个真 `PopupMenu` 并对它调 `show()`，"return nullptr"
等于什么都不可能发生。所以桥既入队又交回对象（`PortSelectPopupMenu`，`show()` 刻意空转
避免双份入队）。
`PortUIBridge.h`：`UIRequestSelect = 5`（编号当初就给它留的）。
harness：`SelectPopup` overlay + ListView（虚拟化/可滚/初始高亮），分隔符/optgroup-label/
disabled 行各自渲染，disabled 选了不答；行下标 == 引擎 listIndex（驱动按引擎顺序发、
每类行都占一格），所以索引直接映射。
`gen-xaml-codebehind.ps1`：EVMAP 补 `SelectionChanged`（ListView 不是 Button；
这个事件是承重墙——用户选哪行就是答案）。
`datalist`（`createSearchPopupMenu`）**故意留 null**：它没有"点了没反应"的可见断裂。

### 2.4 驱动 JIT 门（可调度的稳定性）

`ensureWebCoreInitialized()` 在 `JSC::initialize()` 后**立刻钉死 useJIT**，不再依赖
harness 那个竞态 post；`kDefaultJitDiagnosticMode = 1`（**1.0.0.0 前调试默认开**，
取"JIT thunks 全在、baseline 关"这个最安全形态 = 0.2.4.4 等价行为）。
`WebCoreSetJitEnabled` 收到 enable=1 会拒绝并写 stage.txt。

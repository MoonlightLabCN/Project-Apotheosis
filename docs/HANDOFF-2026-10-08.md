## 1. 崩溃三部曲（真机已验证，别重查）

详见 `docs/JIT-ARM32-R9-ROOT-CAUSE-2026-10-07.md`。摘要：

| # | 崩溃 | 根因 | 状态 |
|---|---|---|---|
| 1 | `VM::jitStubs == nullptr` 被解引用（0.2.5.8 主回归） | `VM::VM` 只在 `if (Options::useJIT())` 建 jitStubs，但 JITThunks 的消费者不看 useJIT（`VM::getCTIStub` 无守卫、`getHostFunction` 的守卫是针对分流的、`InlineCacheCompiler::emitExplicitExceptionHandler` 直接调）；harness 的 `ApplyJitSetting()` post 与 VM 创建竞态 | **已修+验证**：`ENABLE(JIT)` 下改 `Options::useJIT() \|\| ExecutableAllocator::singleton().isValid()` |

### 2.3 `<select>` 下拉弹窗
`PortChromeClient::createPopupMenu` 从 `return nullptr` 改为 `WebCorePort::queueSelectPopup()`。
**关键契约**：WebCore 要求返回一个真 `PopupMenu` 并对它调 `show()`，"return nullptr"
等于什么都不可能发生。所以桥既入队又交回对象（`PortSelectPopupMenu`，`show()` 刻意空转
避免双份入队）。
`PortUIBridge.h`：`UIRequestSelect = 5`（编号当初就给它留的）。
harness：`SelectPopup` overlay + ListView（虚拟化/可滚/初始高亮），分隔符/optgroup-label/
disabled 行各自渲染，disabled 选了不答；行下标 == 引擎 listIndex（驱动按引擎顺序发、
每类行都占一格），所以索引直接映射。
`gen-xaml-codebehind.ps1`：EVMAP 补 `SelectionChanged`（ListView 不是 Button；
这个事件是承重墙——用户选哪行就是答案）。
`datalist`（`createSearchPopupMenu`）**故意留 null**：它没有"点了没反应"的可见断裂。

### 2.4 `<input type=color>` 与 `<input type=date/time>` 选择器（0.2.5.16）

`FEATURE-GAPS §1` 表单缺口的剩下两项，同一条 PortUIBridge 异步路（kind 6/7，
编号当初就预留）。

**桥**（`port/PortUIBridge.cpp`）：
- `queueColorChooser(client, current)` 工厂时入队（当前值已知），payload
  `"<#rrggbb>\t<suggested>..."`；`reattach/setSelectedColor` 又发
  `"\x02current\t<#rrggbb>"`、**同 id 刷新**（壳更新已在显示的卡，不开第二张）。
- `queueDateTimeChooser(client)` **只在工厂交回对象**，真正入队在
  `showChooser(params)`：`DateTimeChooserParameters` 到那一刻才知道，工厂时入队
  只会发给壳一个空请求。payload `"<type>\t<current>\t<min ms>\t<max ms>"`。
- `PortColorChooser`/`PortDateTimeChooser` **自己持原子计数**。`ColorChooser`/
  `DateTimeChooser` 是 `AbstractRefCounted`（纯虚 `ref`/`deref`）；照抄上游
  `EmptyPaymentCoordinatorClient` 加 `RefCounted<>` mixin 反而编不过
  （"member 'operator new' found in multiple base classes"——基类有 TZoneMalloc 的
  operator new）。上游那个文件本就没编进来，所以它的写法从未被验证。
- **日期客户端用 `CheckedPtr` 不是 `RefPtr`**：`DateTimeChooserClient` 是
  `CanMakeCheckedPtr` 而**不是** refcounted（`RefPtr` 直接编不过），裸指针在
  `<input>` 死掉时就是悬垂——和 ScheduledTask 崩溃同一课。
- 颜色解析手写 `#rgb/#rrggbb/#rrggbbaa`（本桥自己产的格式，round-trip 精确），
  不把整个 CSS 颜色 parser + `ScriptExecutionContext` 拖进驱动。

**壳**（`harness/`）：`ColorChooser` 卡 6x7 色板 + 当前色预览（点色块只移预览、
确定才提交，Win10 取色器的"选-确认"节奏）；`DateTimeChooser` 卡按 input type 切
日期/时间框，值**原样**回传（WebCore 校验，壳本地化/重排就是 `"2026-10-8"` 被静默
丢掉的原因）。`ParseWpfColor` 辅助（**别用 designated initializer**，harness 不是
`/std:c++20`）。

## 2.6 软件回退路径修好（0.2.5.17）—— FEATURE-GAPS §0①

ChromeClient 原来按 `g_gpuActive` 取舍，GPU 起不来时整个页面跑上游
`EmptyChromeClient`，于是 **alert/confirm/prompt 静默、`<input type=file>` 点了没反应、
`<select>`/color/date 一个都弹不出来**。软件回退路是 harness 明确保留的
（GpuInit 失败 → 照旧走 Cairo），所以这不是罕见分支。

**修法**：ChromeClient 改为**无条件装配**，把 gate 从"整个 client"下沉到"需要真合成的那几个
钩子"（`PortChromeClient::requestPresent()` 经新增的 `setCompositingPathActive(g_gpuActive)`
控制；`WebCoreGpuInit` 成功时也置位，让已建好的软件会话立刻开始呈现）。

**为什么安全**（逐项核对，见 `docs/FEATURE-GAPS-2026-10-08.md` §0① 的完整清单）：
PortChromeClient 的 UI 工作全走 PortUIBridge 异步请求，**不碰 GL/EGL/ANGLE**；而合成开关
（`setAcceleratedCompositingEnabled` / `setForceCompositingMode`）本来就已经单独 gate 了。
最关键的一条实证：`ChromeClient::scheduleRenderingUpdate()` 上游默认返回 **false**，
PortChromeClient 也返回 false → `Page::scheduleRenderingUpdateInternal()`
（`Page.cpp:2145-2150`）两边都会走 RenderingUpdateScheduler，**行为完全一致**
（没有"白装了 scheduler 导致 rAF 双驱动"的风险）。

## 5. 环境备忘

- **ninja 必须 `-j4`**：12 核 16G 机开默认并行度会 OOM（`docs/JIT-HANDOFF.md` §3 实测；
  本会话作者违反过一次，把用户机器搞 OOM 了）。构建前把进程设 BelowNormal。
- 全量重建常态（改 WTF 头 → 上千 TU），`-j4` 一轮 1006 步约 60-80 分钟。
- 设备息屏 → WDP 超时（ ping 不通就是睡着了，不是崩了）。
- `harness/MainPage.xaml` 改动后必须跑 `port\gen-xaml-codebehind.ps1` 再 `build-harness.ps1`；
  带 `x:Name` 的新控件要**手动**去 `harness\xamlgen\MainPage.g.h` 补字段。
- C++/CX 没 Boolean 隐式装箱；`Platform::Tag` 用 `String^` 当标记最省事。
- **`/std:c++20` designated initializer 在 harness 用不了**（MSVC v143 默认 C++14）：
  `Windows::UI::Color c; c.A=...; return c;`，别写 `Color{.A=...}`。
- 加 `AbstractRefCounted` 派生类时**别照抄上游 `RefCounted<>` mixin**（TZoneMalloc
  operator new 撞车，上游那个文件根本没编进本 port，它的写法从未被验证）。
- **`build-harness.ps1` 输出的 appx 目录名取自构建时的 manifest 版本**：先改版本号
  再构建，否则 appx 还是上一版的（0.2.5.16 的 manifest 配 0.2.5.15 的 appx 目录，
  部署脚本会找不到）。
- 设备当前 `jitdiag.txt = 1`、`testurl.txt` 已删、用户首页设置未被改写。
